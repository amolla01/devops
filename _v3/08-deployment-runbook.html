ansible-playbook -i inventory/hosts.yml playbooks/reused/set_interface_properties.yml \
  -e "admin_status=up" -e "interface_scope=fabric,uplink"

ansible-playbook -i inventory/hosts.yml playbooks/reused/set_interface_properties.yml \

# Dry-run (verify current status, no changes):
ansible-playbook -i inventory/hosts.yml playbooks/reused/set_interface_properties.yml \
  --tags verify

# Skip config save (volatile — lost on reboot):
ansible-playbook -i inventory/hosts.yml playbooks/reused/set_interface_properties.yml \

FLOW Where Interface Configuration Happens in the Deployment Lifecycle

Interface bring-up is embedded in multiple phases. This is the execution order for a full deployment:

PhasePlaybookInterface Actions
Phase 2 (Day-0) deploy_day0.yml → sonic_day0 role Base config_db.json push — sets PORT table with admin_status, speed, and mtu for ALL ports from platform hwsku.json
Phase 3 (Day-1) deploy_day1.yml → sonic_fabric role Fabric links ONLY: Patches PORT table (admin_status=up, speed, mtu={{ fabric_port_mtu }}, fec={{ fabric_port_fec }}). Configures INTERFACE (IPv6 link-local) and BGP.
Phase 4 (Leaf↔Server) deploy_leaf_server_bgp.yml → sonic_leaf_server role Downlink ports: config interface startup <port> + config interface mtu <port> 9000 on each server-facing port
On-demand set_interface_properties.yml → sonic_interface_props role Any combination of admin_status, mtu, speed, fec on any interface scope. Use for troubleshooting, post-deployment tuning, or bulk enable/disable.
Tip: If you need to enable ALL interfaces after a fresh Day-0 push (before Day-1 fabric BGP), run:
ansible-playbook -i inventory/hosts.yml playbooks/reused/set_interface_properties.yml -e "admin_status=up" -e "mtu=9100"
ROLE Role: sonic_interface_props — Internal Task Flow

The sonic_interface_props role (called by set_interface_properties.yml) follows this execution sequence:

StepTask NameWhat It Does
1Parse interface scopeSplits interface_scope into a list (e.g., ["fabric","uplink"])
2Build target interface listCombines host_vars lists (fabric_interfaces, uplink_interfaces, downlink_interfaces) based on scope
3Validate target interfaces resolvedAsserts at least one interface found (fails with helpful message if not)
4Validate propertiesChecks admin_status ∈ {up, down}, mtu ≤ 9216, fec ∈ {rs, fc, none}
5Apply admin_statusconfig interface startup/shutdown <port> for each interface
6Apply MTUconfig interface mtu <port> <value> for each interface
7Apply speedconfig interface speed <port> <value> for each interface
8Apply FECconfig interface fec <port> <mode> for each interface
9Persist configconfig save -y (unless persist_config=false)
10Verifyshow interfaces status <port> and displays results
ALT Legacy Playbooks (dc_modernized_ansible_playbooks/)

Handles ALL SONiC switch types (leafs, spines, border_leafs, routers). Two modes:

ModeFileMechanism

config_db Mode roles/sonic_fabric_switch/tasks/config_db_mode.yml Jinja2 template → config_db.json.j2

The same _v3 playbooks (Day-0 through Sheba Cloud Infra) work on real hardware. Phase 0 + Phase 1 (KVM) are skipped — physical devices are already powered on and cabled.

What changes vs. KVM lab?

ConcernKVM LabReal Hardware
Management NetworkOVS dc-mgmt bridge (172.16.2.0/24)Physical L2 management switch on 172.16.2.0/24 (same subnet, same IPs)
Phase 0 & 1kvm-destroy / kvm-deploySkipped. Switches already running SONiC. Servers PXE-booted or pre-installed.
Platform detectionKVM override: x86_64-kvm_x86_64-r0Auto-detected from DEVICE_METADATA on each switch (Accton, Arista, Celestica)
Port breakoutNot supported (KVM has no ASIC)Supported — config interface breakout via sonic_breakout role
Server NIC nameseth1, eth2 (virtio)enp1s0, enp2s0 (PCI bus names)
SSH transportConservative (workarounds for KVM SONiC SSH quirks)Standard SSH — no workarounds needed
Reload timing15s delay, 180s timeout30s delay, 300s timeout (ASIC init takes longer)
iDRAC/PXEN/A (cloud-init)server_idrac_pxe_map in group_vars for IPMI-based power management

Activation — just change the profile

# Option A: Set in env file (.deploy_lab_v3.env)
AUTOMATION_PROFILE=real_hardware

# Option B: Pass on command line
./deploy_lab_v3.sh --profile real_hardware day0

# Option C: Direct ansible with extra-var override
ansible-playbook playbooks/reused/deploy_day0.yml -i inventory/hosts.yml \
  -e automation_profile=real_hardware

Prerequisites for real hardware

Before running Day-0:
  1. Physical management switch cabled to all device mgmt ports (172.16.2.0/24)
  2. SONiC already installed on all 10 switches (2 spines + 4 leaves + 2 border-leaves + 2 exit-routers)
  3. Ubuntu installed on all 8 servers (can be via MaaS PXE or manual ISO)
  4. SSH access from controller to all devices via 172.16.2.x addresses
  5. server_idrac_pxe_map populated in group_vars/all.yml with real iDRAC IPs + PXE MACs
  6. server_interfaces_real NIC names verified on each server (ip link show)

What the playbooks do differently when real_hardware is active

PlaybookBehavioral Difference
deploy_day0.ymlExtra checks: firmware version assertion, ONIE partition verification, iDRAC reachability
deploy_day1.ymlPort breakout pre-step (if breakout_supported: true): splits 100G ports into 4×25G before BGP config
deploy_server_networking.ymlUses server_interfaces_real (enp1s0/enp2s0) instead of server_interfaces_kvm (eth1/eth2)
deploy_leaf_server_bgp.ymlNo change — operates on downlink_interfaces which are hardware port names in host_vars
All playbooksSSH transport: standard (no conservative workarounds). Longer reload timeouts.
