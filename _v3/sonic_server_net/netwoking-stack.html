OpenStack on Kubernetes Architecture Blueprint

Integration Analysis: Kubespray (Calico) + OpenStack (OVN / ovn-bgp-agent / FRR) on Ubuntu via eBGP

1. Core Architectural Overview

When running OpenStack containerized on top of a Kubespray-deployed Kubernetes cluster, the foundational networking assumptions flip. Kubernetes handles the bare-metal host interfaces, and OpenStack acts as the tenant orchestration framework. By running ovn-bgp-agent alongside FRR to peer natively with an eBGP CLOS fabric, you build a Co-existing Routing Architecture.

Critical System Conflict: Both Calico (via its native BIRD daemon) and host-level FRR will attempt to bind to the default BGP port (TCP 179) on the physical or loopback host interfaces. The engine that registers second will crash, destabilizing cluster-wide ingress/egress mapping.

2. Technical Solution: FRR as the Sole BGP Speaker

To eliminate interface contention, you must completely disable Calico's internal BGP engine and pass the task of advertising all local prefixes (Pods, Services, and Virtual Machine FIPs) exclusively to FRR.

Kubespray Calico Configuration Override

Apply these values inside your Kubespray configuration deployment to disable local BIRD instances and stop Calico's Felix agent from conflicting with OVN interfaces:

# group_vars/k8s_cluster/k8s_net_calico.yml
calico_no_global_bgp_peers: true
calico_network_backend: "none"
calico_felix_interface_exclusion: "br-int,br-ex,bgp-nic,ovn-*"

Host System FRR Engine Matrix

Update your Ubuntu host /etc/frr/frr.conf layout to aggregate routes out of both ecosystem environments seamlessly:

router bgp 65001
 bgp router-id 192.168.10.11
 no bgp ebgp-requires-policy
 
 neighbor 10.0.0.1 remote-as 65100
 neighbor 10.0.0.1 description Leaf-Switch-A
 
 address-family ipv4 unicast
  redistribute kernel route-map FILTER-TO-FABRIC
  redistribute connected route-map FILTER-TO-FABRIC
  neighbor 10.0.0.1 activate
 exit-address-family

ip prefix-list ALLOWED-PREFIXES seq 10 permit 10.233.0.0/18 le 32
ip prefix-list ALLOWED-PREFIXES seq 20 permit 10.233.64.0/18 le 32
ip prefix-list ALLOWED-PREFIXES seq 30 permit 203.0.113.0/24 le 32

route-map FILTER-TO-FABRIC permit 10
 match ip address prefix-list ALLOWED-PREFIXES

3. Strict Multi-Tenancy & Security Isolation

To prevent address overlapping conflicts across isolated account environments, private tenant allocations are containerized inside OVN software-defined **Geneve overlay tunnels**. The host's public edge interfaces handle outer encapsulation headers only.

  • expose_tenant_networks = False inside ovn-bgp-agent.conf to enforce encapsulation boundaries.
  • expose_floating_ip = True to strictly permit public endpoint routing visibility via host FRR.
  • Isolate external provider lanes by pinning host-level FRR configurations into an independent network VRF namespace on Ubuntu.

4. Cross-Account Interconnect Matrix

When a tenant sets up resources over independent accounts and requires cross-boundary links, evaluate the following platform configuration options:

Connectivity Model Architectural Method Trade-Off Advantages System Constraints
Option 1: OVN Router Peering Direct internal software bridging via tenant RBAC tokens inside the OVN layer. [+] Maximum line-rate routing processing speed.
[+] Consumes no Floating IPs.		 [-] Overlapping private IP subnets are strictly blocked.
Option 2: External Floating IPs Traffic routes outward across the eBGP fabric and hairpins back via dual NAT translation. [+] Absolute data isolation.
[+] Allows completely overlapping tenant CIDRs.		 [-] Noticeable dual-NAT latency penalty.
[-] Heavy external IP pool allocation overhead.
Option 3: Address Scopes Pre-mapped global address definitions route directly via host Provider Networks. [+] Bypasses all processing overhead associated with NAT. [-] Imposes continuous up-front routing setup coordination.
Option 4: Tenant VPN Overlay Crypto gateway appliances (WireGuard/IPsec) running straight inside the tenant VMs. [+] Completely decoupled; zero administrative overhead. [-] Triple-encapsulation layers cripple MTU efficiency.
