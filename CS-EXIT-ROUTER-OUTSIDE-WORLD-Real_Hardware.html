2. Overview & Traffic Flow

2.1 Egress (Host downloads from the internet)

Host12_1 (10.10.255.1) — FRR default route via BGP │ ▼ Leaf_L1 (Accton AS5712, AS65011) / Leaf_L2 (AS65012) │ Ethernet68/64 → 40G QSFP+ ▼ Spine_S1 (Celestica DX010, AS65000) / Spine_S2 (AS65000) │ Ethernet16/20 → 100G→40G breakout ▼ Border_Leaf1 (Arista 7050QX-32S, AS65021) / Border_Leaf2 (AS65022) │ Ethernet0 — 10G breakout sub-port 0 ▼ Exit_Router1 (MikroTik CRS326, AS65253) / Exit_Router2 (AS65254) │ ether1 — MASQUERADE (SNAT) ▼ Internet / WAN

2.2 Ingress (External user accesses a service inside)

Internet / User │ ▼ Exit_Router ether1 ── DST-NAT (DNAT port forward) ── translate to internal IP:port │ ▼ Border_Leaf ── eBGP ── Spine ── eBGP ── Leaf │ ▼ Host (VM/bare-metal service)

On physical Arista 7050QX-32S, the QSFP+ breakout must be configured before the port comes up as 10G sub-interfaces. This is done in the border-leaf breakout_cfg within host_vars/Border_Leaf1.yml. 5. Deployment Procedure (Step-by-Step)

5.1 Prerequisites — Real Hardware Specific

  • All physical cables seated and confirmed (especially border-leaf Ethernet0 ↔ exit router sfp+1).
  • Border-leaf QSFP+ port 1 already broken out as 4×10G (done by SONiC day-0 playbook).
  • Exit routers powered on; RouterOS 7.x running; reachable via SSH at 172.16.2.98/99 through management network.
  • External interface (ether1) connected and ISP/campus uplink live.
  • Profile exported: export AUTOMATION_PROFILE=real_hardware

5.2 Execution Order

1 Configure the /31 fabric link (SONiC side)
export AUTOMATION_PROFILE=real_hardware
ansible-playbook playbooks/deploy_day1_v2.yml \
  -i inventory/hosts.yml \
  --limit border_leaves,exit_routers
Configures eBGP P2P link on Border_Leaf Ethernet0. Uses sonic_fabric/tasks/main_v2.yml which includes exit_interfaces in _fabric_links even when spines are not in the limit.
2 Deploy full exit router configuration
ansible-playbook playbooks/deploy_exit_routers.yml \
  -i inventory/hosts.yml
Runs all 6 phases: preflight → base → BGP → NAT → firewall → verify.
3 Verify end-to-end reachability from a host
ssh admin@172.16.2.x "ping -c 3 8.8.8.8"
If successful, the default route and masquerade are working end-to-end on physical hardware.
4 (Optional) Add inbound port forwards
Add DNAT rules for services you want externally accessible. See Section 9.
No KVM proxy needed

Unlike win11_kvm, there is no SSH proxy command or jump host for exit router access. The deployer machine connects directly to 172.16.2.98/99 via the management network (172.16.2.0/24).

6.2 Default route propagation path (physical fabric)

Exit_Router1 (AS65253) → Border_Leaf1 (AS65021)
  → Spine_S1/S2 (AS65000)
    → Leaf_L1 (AS65011), Leaf_L2 (AS65012), Leaf_L3 (AS65013), Leaf_L4 (AS65014)
      → Host12_1/2/3, Host34_1/2, HostB12_1/2 (FRR: via eBGP)

Exit_Router2 (AS65254) → Border_Leaf2 (AS65022)
  → Spine_S1/S2 (AS65000)
    → all leaves → all hosts

Every host receives two ECMP default routes — one per exit router. BGP failover is automatic if one exit router goes down. On physical hardware, BGP timers are not inflated by KVM vCPU scheduling lag, so convergence is faster.

7. NAT — Source NAT (Masquerade)

7.1 Rules applied to each exit router

/ip firewall nat add chain=srcnat out-interface=ether1 \
  src-address=10.0.0.0/8 action=masquerade comment=fabric-snat-10.0.0.0_8

/ip firewall nat add chain=srcnat out-interface=ether1 \
  src-address=172.16.2.0/24 action=masquerade comment=fabric-snat-172.16.2.0_24

7.2 What each range covers in the physical fabric

SNAT Source RangeCovers
10.0.0.0/8All loopbacks (10.0.x.x), host BGP loopbacks (10.10.255.x), P2P fabric links (10.0.253.x), VTEPs
172.16.2.0/24Management IPs of all switches (Spines, Leaves, Border Leaves, Exit Routers) and host management
Physical MTU path

All fabric links and sfp-sfpplus1 are configured for jumbo frames (MTU 9216). Ensure the upstream ISP link on ether1 can handle the MTU or that MSS clamping is in place to avoid fragmentation on egress.

9. Inbound Access (Port Forwarding / DNAT)

To expose an internal service to the outside world, add a DNAT rule on the exit router. Not automated by default — add manually or extend the playbook with a DNAT task.

9.1 Example: Expose Horizon dashboard (Host12_1)

/ip firewall nat add chain=dstnat in-interface=ether1 \
  protocol=tcp dst-port=8080 \
  action=dst-nat to-addresses=10.10.255.1 to-ports=80 \
  comment="Inbound: Horizon → Host12_1:80"

9.2 Example: MaaS UI (HostB12_1)

/ip firewall nat add chain=dstnat in-interface=ether1 \
  protocol=tcp dst-port=5240 \
  action=dst-nat to-addresses=192.168.255.31 to-ports=5240 \
  comment="Inbound: MaaS → HostB12_1:5240"

9.3 Firewall addition for DNAT

/ip firewall filter add chain=forward action=accept \
  in-interface=ether1 connection-state=new connection-nat-state=dstnat \
  comment="Allow DNAT forwarded connections" \
  place-before=2
Security Warning

Each DNAT rule directly exposes an internal host to the internet. On physical hardware the risk is real. Restrict to the minimum ports needed and ensure the target service has its own authentication.

# Routes received from border-leaf:

# Verify default route is being advertised:
/routing bgp advertisement print

# NAT rules:
/ip firewall nat print stats

# Firewall counters:
/ip firewall filter print stats

# Ping internet from router:
/ping 8.8.8.8 count=3

# Ping border-leaf fabric IP:
/ping 10.0.253.0 count=3

10.3 From a physical host server

# Test egress (internet):
ping -c 3 8.8.8.8
curl -s -o /dev/null -w "%{http_code}" https://google.com

# Trace path to internet (should show 2 physical switch hops → exit router → internet):
traceroute -n 8.8.8.8

# Check FRR default routes (should show 2 ECMP paths — one per exit router):
vtysh -c "show ip route 0.0.0.0/0"
ip route show default

ssh admin@172.16.2.31
vtysh
  show bgp summary
  show bgp neighbors 10.0.253.1
  show ip route 0.0.0.0/0

12. Troubleshooting

SymptomLikely CauseFix
Host cannot ping 8.8.8.8 BGP not established / no default route in FRR vtysh -c "show bgp summary" on border-leaf; check exit router BGP session
BGP stuck in Connect between border-leaf and exit router Physical cable not seated, or port not up as 10G (breakout not applied) Check show interface Ethernet0 on border-leaf; confirm breakout config; re-seat cable
BGP established but no default route propagated output.default-originate not set, or exit router has no default route itself Check /routing bgp advertisement print on exit router; confirm ether1 has a gateway
Host can ping 8.8.8.8 but TCP connections fail MTU mismatch — jumbo MTU 9216 on fabric, ISP expects 1500 Add MSS clamping on ether1: /ip firewall mangle add chain=forward protocol=tcp tcp-flags=syn action=change-mss new-mss=clamp-to-pmtu out-interface=ether1
Host gets response from internal but not external NAT masquerade not matching or ether1 has no routable IP /ip firewall nat print stats — check byte counter on masquerade rules; verify ether1 IP
deploy_exit_routers.yml SSH connection refused Exit router unreachable on 172.16.2.98/99 Verify management switch port48/49 uplinks; check ether24 IP on exit router via console
deploy_day1_v2.yml --limit border_leaves,exit_routers fails: no interfaces match Using old sonic_fabric/main.yml which misses exit_interfaces Ensure you are running deploy_day1_v2.yml which references sonic_fabric/tasks/main_v2.yml
Asymmetric path (in via Router1, out via Router2) ECMP load balancing — expected behavior Not a problem; connection tracking on RouterOS handles masquerade state correctly across asymmetric paths
